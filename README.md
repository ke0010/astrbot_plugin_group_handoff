# 群聊接力 · Group Handoff

> 同一个群里有两个机器人，你 @ 一句话，它们不该抢着同时开口，也不该各说各的。

这是一个 [AstrBot](https://github.com/AstrBotDevs/AstrBot) 插件。它让同一个群里的多个机器人**轮流说话**：先抢到发言权的人先说，另一个先等它说完——而且等完之后，它读到的上下文里**已经包含对方刚说的那一句**。

---

## 一、这解决什么问题

### 现象

群里放着两个机器人（比如柯莱和芙宁娜——对，就是这两个名字）。你在群里 @ 一句"晚上吃什么"，两秒之内：

- 两个机器人**同时**开始生成
- 各自都看不见对方说了什么
- 结果要么抢话，要么两句完全对不上，像两个人在各自打电话

AstrBot 本身没有"跨机器人协调"的能力：两个机器人各跑各的管线，谁也感知不到谁。

### 为什么"发之前等两秒"不管用

最直觉的修法是在**发送前**延迟两秒。但没用，因为 AstrBot 的管线是这样的：

```
收到消息 → 取会话锁 → 组装 prompt（读历史） → 调 LLM → 分段发送
```

你在"发送前"等，prompt 早就组装完了——模型看到的还是对方没说话的世界。等多久都接不上。

### 本插件的做法：换一个位置等

```
收到消息 → 取会话锁 → 组装 prompt → 调 LLM → 发送
                    ↑
              插件在这里动手
```

插件挂在 `OnWaitingLLMRequestEvent` 上——**"准备调用 LLM、但上下文还没组装"**的那个时刻。在这里先看群里有没有别的机器人正在说话：

- 有 → 等它说完（`max_wait_seconds` 兜底），再放行
- 没有 → 立刻放行，多花 0.02 秒

放行之后，管线才去组装 prompt。此时对方刚说的那句**已经躺在群历史里**，模型自然就能接上话。

## 二、安装

**要求**：AstrBot `>=4.19,<5`，平台 `aiocqhttp`（QQ 个人号 / NapCat 等）。

### 方式一：手动（推荐，最简单）

把本目录整个拷到 AstrBot 的插件目录：

```
<AstrBot 数据目录>/plugins/astrbot_plugin_group_handoff/
```

重启 AstrBot。日志里出现下面这行就说明加载成功：

```
[group_handoff] 已加载 me=xxxxxxxx 目录=... 白名单=全部群 最长等待=20.0s
```

### 方式二：git clone

```bash
cd <AstrBot 数据目录>/plugins
git clone https://github.com/ke0010/astrbot_plugin_group_handoff.git
```

然后重启。

### 装几份？

**只需一份。** 同一个 AstrBot 实例里挂多个平台（多个 QQ 号）时，插件是在进程内共享的，通过 `self_id` 区分是哪个机器人。如果你的两个机器人分别跑在**两个 AstrBot 实例**里（两个进程），那两边各装一份即可，靠 `shared_dir` 指向同一个目录来通信。

## 三、配置

后台「插件」页点进本插件即可改配置，配置文件是 `data/config/astrbot_plugin_group_handoff_config.json`。

| 键 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `enabled` | bool | `true` | 总开关 |
| `group_whitelist` | list | `[]` | 生效的群号列表；**留空 = 所有群**。建议填上，避免误伤别的群 |
| `max_wait_seconds` | float | `20` | 最多等对方多久（秒）。等满就先开口，不会无限挂住 |
| `floor_ttl_seconds` | float | `120` | 发言权标记的有效期。防止对方崩溃后标记永远不释放 |
| `poll_interval_seconds` | float | `0.3` | 轮询间隔。调小更灵敏但更费 CPU/磁盘 |
| `gap_min_seconds` | float | `1.0` | 对方说完后，自己再停顿的最短时间 |
| `gap_max_seconds` | float | `2.5` | 对方说完后，自己再停顿的最长时间（随机取值） |
| `shared_dir` | str | `""` | 状态目录。留空 = 系统临时目录下的 `astrbot_group_handoff` |

**调参建议**

- 群里就两个机器人：`gap_min/max` 用默认 1.0~2.5 秒，听起来最像人
- 三个以上机器人：`max_wait_seconds` 调到 30，防止第三个等太久
- 只想在某个群用：`group_whitelist` 填那个群的群号（在 AstrBot 后台的平台日志里能看到）

## 四、"说完"是怎么判定的

插件挂在 `OnAfterMessageSentEvent` 上，这个事件在**所有分段都发完之后**才触发（如果开了分段回复，会等整段发完，而不是第一段）。触发时释放发言权，另一个机器人的等待循环读到释放，再随机停顿 `gap` 秒后开口。

如果对方中途报错、进程崩了、回复被拦截，`OnAfterMessageSentEvent` 就不会触发——这时靠 `floor_ttl_seconds`（默认 120 秒）兜底：标记过期后，等待方视为"对方不说了"，自己接着开口。

## 五、已知限制（请先看完再用）

1. **只支持同一台机器上的多个实例。** 状态靠共享目录里的一个小 JSON 文件同步，没有中心服务器、没有网络请求。两个机器人跑在两台电脑上？不行，本插件不解决这个问题（也不想为了它引入一个服务端）。
2. **极端情况下会多等。** 对方崩溃没释放标记时，等待方最多等满 `max_wait_seconds` 才开口。想更快就调小这个值，代价是对方只是说话慢一点时你可能抢话。
3. **只对群聊生效。** 私聊不触发。
4. **不保证固定顺序。** 谁先抢到谁先说，不保证"柯莱永远先说"。想固定顺序应该用别的方式（比如只 @ 一个人）。
5. **不改变回复内容。** 插件只控制时机，从不说任何话、不往群里发任何消息。群成员看到的唯一区别就是"第二个机器人慢半拍"。
6. **单机器人的群装它也没坏处**，只是多 0.02 秒判断。

## 六、调试

在 AstrBot 日志里搜 `[group_handoff]`：

- `已加载 me=... 目录=...` —— 加载成功，看目录对不对
- `等满 20.0s，...仍被占用，先开口` —— 对方没释放，走了超时兜底
- `... 等对方说完，再停 1.8s 后开口` —— 正常工作
- `等待逻辑出错，按原样继续` —— 有异常但已兜底，插件不会卡住回复

**查状态文件**：默认在 `%TEMP%\astrbot_group_handoff\floor_<平台>:<群号>.json`，内容大致是：

```json
{"owner": "1234567890", "self_id": "1234567890", "ts": 1730000000.0}
```

`owner` 是当前持有发言权的机器人 QQ 号。正常情况下，对方说完后这个文件会被删掉。

**常见问题**

| 症状 | 原因 |
|---|---|
| 没生效 | 群不在 `group_whitelist` 里 / 两个 bot 不在同一 AstrBot 实例 / 插件没加载成功（看日志第一行） |
| 等很久才说话 | 对方崩了没释放，`floor_ttl_seconds` 兜底中；或 `max_wait_seconds` 太大 |
| 两个还是同时说 | 两个 bot 在不同电脑 / 不同 AstrBot 实例但 `shared_dir` 没指向同一目录 |
| 状态文件一直不删 | 对方没触发 `OnAfterMessageSentEvent`（被拦截/报错），等 TTL 过期即自愈 |

## 七、版本

跟随 AstrBot **4.29** 开发并验证。后续版本不保证一直可用——钩子的触发位置如果变了，这个插件可能"加载成功但没效果"。遇到问题请提 issue，带上 AstrBot 版本号和 `[group_handoff]` 相关日志。

## 彩蛋

这个插件是为一个具体的场景写的：一个群，两个机器人，一个在化城郭守着雨林，一个在须弥城当大明星，中间坐着她们共同的那个人。深夜聊天的时候，两个人都想说话，但谁都不该抢话。

代码里没有她们的名字，但写的时候一直在想那间屋子。
